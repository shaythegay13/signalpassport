## 2. Task 0: Zero-Evidence Throw Fix

### Defect Identified (Pre-M4)
Prior to M4, `computeDeterministicMetrics` unconditionally instantiated claims with:
```ts
evidenceIds: evidence.map((e) => e.evidenceId)
```
When `evidence = []`, `claimSchema.evidenceIds` threw `evidenceIds must be non-empty (path: evidenceIds)`.

### Fix Applied
In `packages/analysis/src/metrics.ts`, claim creation was made conditional per metric. If no backing evidence exists for a metric, no claim is added to the `claims` array. When `evidence = []`:
- `claims` evaluates strictly to `[]`.
- `metrics` evaluates to `{ observedTransactionCount: 0, activeDays: 0, uniqueRecipients: 0 }`.
- `PassportPayload.claims` accepts `[]` per `z.array(claimSchema)`.

### Verification Evidence
- Unit test in `tests/zero-activity.test.ts`:
  ```ts
  const result = computeDeterministicMetrics([], testScope);
  assert.deepEqual(result.claims, []);
  assert.equal(result.metrics.observedTransactionCount, 0);
  assert.equal(result.metrics.activeDays, 0);
  assert.equal(result.metrics.uniqueRecipients, 0);
  ```
- Result: **PASS** (committed independently in commit `ca74b33`).

## 5. Task 3: Provider Unavailable Surfacing (Never Zero Activity)

### The Invariant (PRD §14)
> Provider downtime, upstream 5xx errors, timeouts, or rate limits must NEVER be conflated with a valid zero-activity wallet.

### Behavior in App One
When an upstream failure occurs (e.g. Blockscout HTTP 503, connection refused, or simulated via testing control):
1. The route streams an error stage event:
   ```json
   {
     "stage": "error",
     "error": "Upstream data provider unavailable: Blockscout REST v2 connection refused (HTTP 503). Service temporarily unreachable.",
     "statusCode": 503,
     "isProviderError": true
   }
   ```
2. App One halts the pipeline and renders a dedicated **Provider Unavailable Error Card**:
   - Header: **Provider Unavailable (Upstream Infrastructure Failure)**
   - Badge: `badge-danger` ("Operational Failure")
   - Error details: Exact upstream failure explanation
   - Callout: *"PRD §14 Invariant: Upstream provider unavailability, HTTP 5xx errors, and rate limits are operational infrastructure failures. They are never treated as zero activity and must never generate an empty passport."*
3. No zero-activity passport or metrics are generated.

## 6. Task 4: Partial Coverage Surfacing

### Generation & Evaluation
When pagination is limited before exhausting history (e.g. `maxPages: 1` or upstream page limit reached with `hitPageLimit: true`):
- `evaluateCoverage` computes `coverageStatus: "partial"`, `isTruncated: true`, `pageCount: 1`.
- The sealed bundle records `payload.coverage.coverageStatus === "partial"`.

### Display in App One
- Coverage Status badge in metadata grid: `<span className="badge badge-warning">partial</span>`
- Prominent warning box:
  > **Warning: Partial Coverage (PRD §14).** Upstream pagination limit reached before exhausting the 30-day window (1 page(s) retrieved). Metrics reflect only observed transactions within available pages and are NOT complete for the entire query scope.

### Display in App Two
- When imported, App Two verifies the bundle and preserves `coverageStatus: "partial"`.
- Coverage Status badge: `<span className="badge badge-warning">partial</span>`
- Prominent warning box:
  > **Warning: Partial Coverage (PRD §14).** This passport bundle reflects incomplete transaction history within the declared observation window (1 page(s) retrieved). Downstream systems should note that activity may be undercounted.
